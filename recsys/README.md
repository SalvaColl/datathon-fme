# recsys — v1 candidate generation + gradient-boosting purchase model

Owner: Javi · branch `javi/v1-gbm-recommender` · status: **challenger, dry-run only** (not the live writer).

## What it does (product-manager version)

For every shopper we gather ~150–300 plausible products (what they just viewed, the strongest products of that
subcategory/category, products they looked at or carted in the past, new products of that category), score each one
with a model that predicts "will this shopper buy this product if we show it", and show the 10 highest, best first.

## Run

```bash
cd recsys
pip install -r requirements.txt          # pinned sklearn: the committed model needs the same version
python download_sessions.py              # -> data/hs.parquet            (~4 min, 2M sessions)
python download_user_items.py            # -> data/user_item_{A,all}.parquet (~2 min)
python live.py --dry-run                 # computes answers + latency, writes NOTHING
python live.py --ab                      # LIVE, 50/50 by user hash: baseline-ctrl vs v1-gbm-cand (one writer!)
python live.py                           # LIVE, 100% model — only if it REPLACES the current team writer
python compare_versions.py 60            # realized conversion / latency per model_version, last 60 min
```

`.env` is read from `recsys/` or the repo root. `data/catalog.parquet` and `data/model_buy.joblib` are committed;
everything else in `data/` is git-ignored and regenerated by the download scripts.

To retrain: `python train.py` (needs `data/hs.parquet` + `data/user_item_A.parquet`), then `python ev.py`.

## Files

| File | Role |
|---|---|
| `fe.py` | Feature engineering shared by training and serving (`build_tables`, `featurize`, `FEATS`) |
| `train.py` | Builds 2.5M (session, shown item) rows, trains `HistGradientBoostingClassifier` → `data/model_buy.joblib` |
| `ev.py` | Within-session ranking evaluation on the time-split holdout (hit@1 / MRR of purchased item) |
| `live.py` | pull → predict → push loop: catalog/stock refresh, incremental live-event tables, candidates, model, guards |
| `rt.py` | Tiny RawTree query helper (`python rt.py "SELECT ..."`) |
| `explore_*.py` | The exploratory analyses behind the insights in `../insights.md` (I-010 … I-015) |

## Features (`fe.FEATS`)

Session: in recent views / count / is last viewed / position, same subcategory / category / brand as last view,
any viewed subcategory, number of views, page. Item: log views/carts/purchases, purchase rate, cart rate, log price,
price relative to last viewed, age. User (organic history): user×item views/carts/purchases, user×subcategory and
user×category views/purchases, user totals, known user, new user. `slot` is a training feature and set to 0 at serving.

## Live safety

- Never recommends inactive / out-of-stock products (catalog + `catalog_updates` refreshed every 20 s).
- Always exactly 10 distinct ids; pads/falls back to in-stock best sellers on any error.
- Deadline guard: a request already >1.8 s old when we get to it is answered instantly with the fallback slate
  (`model_version = v1-gbm-cand-guard`) instead of being late.
- Each push is retried once (a lost batch = `missing` for every request in it).
- Live events are aggregated incrementally (O(new events) per refresh) so latency does not grow during the night.
- Dry-run measured (14 Nov ~13:00 CET, 5 × 60 requests): request age at answer p50 0.6–0.7 s, p95 0.9–1.5 s,
  max 1.9 s, model ~50–120 ms per batch. Push adds one HTTP call per batch.

## Known limitations / next steps

- Offline evaluation only ranks within logged slates (all from one category); candidate generation outside those
  slates is not validated offline — the practice leaderboard is the real test.
- Count features: model trained with 30 days of user history, served with 60 days + live (scale shift).
- No explicit exploration, trend, or text-based cold-start yet (I-002, I-004, I-007).
