## Narrow code changes

Current main holds feature_lock across the entire grouped event backlog. K28 applies exactly the same deltas in the same order, but releases that lock after each 64-row chunk and yields to foreground requests. A mock integration checks all LiveTables/AP/LF increments, bought exclusions and the final checkpoint; a concurrent test proves foreground access before the backlog finishes. This does not accelerate pre-ready model/history initialization or guarantee a millisecond bound on a single slow row. It changes feature-update granularity, so request-time snapshots can be partial rather than waiting for the whole batch.

Current main also waits for POST acknowledgement before polling again. K28 optionally overlaps the NEXT read-only request poll with that wait. RequestReader is one daemon thread inside the existing process, with its own thread-local HTTP Session. It cannot predict, claim journal entries or POST submissions. The original main thread remains the ONLY writer and owns all SQLite calls. Duplicate queue entries are merged; main rechecks seen IDs and durable attempts before any inference/write. Buffer is bounded (256 records); stale observations are dropped, dispatch still applies the original 1.8s guard and 2.5s send cutoff. Short capped backoff handles read failures. No blind submission retry was added.

Default: no extra queries. When disabling, an in-flight read is allowed to finish and its queue drains before serial polling resumes; no second request-poll stream is started during the transition. Inactive reader thread waits without polling. This is not a second recommender or second submitter.

Instrumentation separates wait/query time, request age on consumption, inference, validation/journal preparation, POST time, journal completion, queue wait, expiry and stock age. Empty-loop heartbeats appear every five seconds, and read errors are counted/logged with throttling. `oldest_age_ms` now considers only the actually sent subset. Preserve source UTC timestamps; don't clamp away apparent clock skew.

A fully mocked integration test holds a fake POST acknowledgement while the reader discovers another fake request, then verifies each request is posted once by the main thread, with the existing public alias mapping. No network, real model initialization, real journal/lock or live producer is used. Full suite: **124 tests passed** (includes Windows-only night-lab assertion portability correction).

| Assumed network profile | Serial on time | K28 on time | Serial / K28 p95 (ms) | Serial / K28 read queries |

Zero duplicate attempts in all simulated cases. These are ENGINEERING SIMULATIONS, not measured production performance or expected conversion. Server receipt is modeled at half POST RTT. Real API limits/contention, socket timeouts, CPU/locks, journal costs and live metadata updates are not modeled. K28 makes roughly 2.6–3.6 times as many request-query calls in these scenarios; API/mobile-link contention could make it worse. Neither mode fixes an outage. **Do not promise 100%, or promote using this table.** Requests timeouts are socket inactivity limits rather than hard wall-clock deadlines (https://requests.readthedocs.io/en/stable/user/advanced/).
